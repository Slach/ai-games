# Правила AI Game Master

## Обзор игры

AI Game Master — это кооперативная игра с генерируемым искусственным интеллектом сюжетом,
доставляемая через Telegram-бот. Каждый ход генерируется уникальная история в космическом
сеттинге (звёздный корабль, экипаж, приключения), где игроки принимают решения,
влияющие на развитие сюжета.

## Основные механики

### 1. Регистрация и онбординг

- После `/start` игрок проходит интервью (5+ вопросов с вариантами)
- Вопросы генерируются LLM, каждый вариант содержит очки (role_scores) для ролей
- Дополнительные вопросы определяют вид (species) и пол (gender) персонажа:
  - 10 вопросов о виде (человек, гуманоид, негуманоид, энергия, кибернетика, симбиот)
  - 4 вопроса о поле (мужской, женский, нейтральный, сменяемый, множественный и т.д.)
- На основе ответов через ComfyUI генерируется аватар с учётом вида/пола
- Роль назначается детерминированно по максимальной сумме очков (role_scores)
- После онбординга игрок получает роль, описание, вид, пол, аватар

### 2. Формирование экипажа

- **GAME_START_MIN_PLAYERS** (по умолчанию 3) — минимальное количество живых игроков для старта
- Свободные места на старте занимают **NPC** — ровно до **NPC_COUNT = 4** мест,
  с приоритетом ключевых ролей `chief_engineer` / `medical_officer` / `pilot` / `science_officer`
- Живой игрок, завершивший онбординг, может **занять место NPC** в той же роли
- NPC освобождает роль, если живой игрок получает ту же роль
- Место кикнутого или погибшего игрока **не заменяется NPC** — оно остаётся пустым
  до конца игры; экипаж не пополняется автоматически
- При завершении онбординга всем остальным игрокам рассылается **уведомление с аватаром и профилем**

### 3. Старт игры и миссия

При старте игры (когда набрано GAME_START_MIN_PLAYERS живых игроков):

1. **Генерация NPC** — для свободных ключевых ролей (до NPC_COUNT = 4 мест)
   создаются NPC с аватарами:
   - Без онбординга и интервью
   - Вид (species) и пол (gender) выбираются случайно
   - Prompt для аватара генерируется рандомно для разнообразия
   - Каждый NPC получает стартовую **лояльность** 70/100 (см. «Лояльность NPC и мятеж»)
2. **Генерация миссии** — LLM создаёт:
   - Название и описание миссии
   - Цели миссии с разбивкой на **этапы** (stage-based progression)
   - Каждый этап имеет требования для завершения
   - Данные миссии хранятся отдельно (таблица `game_missions`)
   - Учитываются при генерации каждого следующего хода
3. **Генерация картинки рубки** — сложный image pipeline:
   - LLM генерирует промпт с учётом всех ролей и аватаров
   - Аватары команды используются как **reference изображения** (ControlNet/IP-Adapter)
   - Единая сцена: мостик корабля с командой на своих постах
4. **Брифинг миссии** — всем игрокам рассылается:
   - Описание миссии и целей
   - Сгенерированная картинка рубки с командой

## Алгоритм каждого хода (turn)

```text
┌─────────────────────────────────────────────────────────────────┐
│  НАЧАЛО ХОДА                                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. Генерация общей вводной на основе предыдущего хода:        │
│     - Если есть предыдущий ход — учитываются последствия       │
│     - Учитывается текущее состояние миссии и этапы             │
│     - Создаётся описание ситуации на корабле и вокруг          │
│                                                                 │
│  2. Генерация промпта для картинки по общей вводной           │
│     → Генерация картинки через ComfyUI                         │
│                                                                 │
│  3. Генерация брифинга для КАЖДОГО игрока:                    │
│     - Персональная вводная (что видит/слышит этот персонаж)   │
│     - 5 вариантов действий (квота 2/2/1 по типам)              │
│     - У каждого действия есть СКРЫТОЕ последствие              │
│     - Часть последствий ухудшает состояние, часть улучшает     │
│     - Последствия имеют коэффициенты влияния (запоминаются)    │
│                                                                 │
│  4. Генерация промпта индивидуальной картинки брифинга        │
│     → Генерация картинки через ComfyUI                         │
│                                                                 │
│  5. Отправка живым игрокам:                                    │
│     - Общая вводная + общая картинка                           │
│     - Индивидуальный брифинг + индивидуальная картинка         │
│     - Варианты действий + дедлайн хода                         │
│       («Ход закроется: ...» UTC)                               │
│                                                                 │
│  6. Сбор ответов от живых игроков:                             │
│     - Напоминания T-2h и T-30m до дедлайна                     │
│     - Не выбравшим — авто-выбор действия (LLM),                │
│       при сбое LLM фиксируется ПРОМЕДЛЕНИЕ (delay)             │
│                                                                 │
│  7. Как только ВСЕ живые игроки ответили:                     │
│     - Вводные передаются NPC                                   │
│     - NPC выбирают действия НЕ ЗНАЯ последствий                │
│     - NPC не видят выборов других игроков                      │
│                                                                 │
│  8. Анализ ВСЕХ выбранных последствий:                        │
│     - Генерация общих последствий (combined outcome)           │
│     - LLM возвращает ДЕЛЬТЫ корабля и события по entity_id,    │
│       абсолютное состояние считает код                         │
│     - Действия игроков имеют БОЛЬШИЙ вес, чем NPC             │
│     - Проверка достижения целей миссии                         │
│       → Этапы могут достигаться НЕЛИНЕЙНО, эффект накапливается│
│     - Шкала угрозы растёт каждый ход (+8 и ускорители)         │
│     - Если цели достигнуты → оповещение живых игроков          │
│                                                                 │
│  9. Допускается:                                               │
│     - Ранения (нарастают: minor → moderate → critical)         │
│     - Гибель членов экипажа (в т.ч. критическая рана           │
│       + любая новая рана = смерть)                             │
│     - Гибель корабля: корпус 0 = конец (решает код)            │
│     - Гибель всего экипажа (crew_wiped) достижима —            │
│       экипаж не пополняется                                    │
│                                                                 │
│ 10. Для мёртвых членов экипажа (не NPC):                      │
│     - На каждом ходу генерируются последствия и вводные        │
│     - Они остаются зрителями (видят, но не влияют)             │
│     - Мёртвый игрок может нажать /start                        │
│       → присоединиться к новой игре                            │
│       → или к текущей в новой роли (заняв место NPC)           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Ключевые принципы:**

- Действия игрока влияют на последствия **сильнее**, чем действия NPC
- Прогресс миссии нелинейный — правильные действия накапливают прогресс
- Состояние корабля, раны, угроза и лояльность — персистентное состояние игры
- Проиграть можно пятью способами: угроза 100, корпус 0, весь экипаж погиб,
  мятеж NPC, провал миссии (см. «Матрица исходов»)

## Поведение Game Master (корабельный компьютер)

### При начале нового хода

1. **Проверка состояния игры**
   - Проверяет, что игра не закончена (корабль и экипаж живы)
   - Проверяет, все ли живые игроки ответили
   - Если игра закончена — генерация прекращается

2. **Генерация сюжета**
   - Учитывает последствия предыдущего хода
   - Учитывает прогресс миссии и этапов
   - Обеспечивает связность и последовательность истории

3. **Генерация контента**
   - Общая картинка через ComfyUI
   - Индивидуальные картинки брифингов

4. **Обработка действий**
   - Живые игроки выбирают первыми
   - NPC выбирают после (без знания последствий)
   - Анализ последствий с учётом веса игроков

## Взаимодействие с игроками

### Текстовые сообщения

- Игроки могут общаться с Game Master в любое время
- Game Master отвечает в характере корабельного компьютера

### Голосовые сообщения

- Запись и хранение

## Игровые механики

### Действия и последствия

- Каждое действие имеет видимый текст и **скрытое последствие** с типом
  (`consequence_kind`): `progress` / `injury` / `fatal`
- Квота вариантов в брифинге: **2 progress / 2 injury / 1 fatal** (по умолчанию,
  настраивается `GAME_TURN_PROGRESS_ACTIONS` / `GAME_TURN_INJURY_ACTIONS` /
  `GAME_TURN_FATAL_ACTIONS`)
- Тип варианта скрыт от игрока — выбор вслепую; текст действия не выдаёт исход
- Метка последствий — обязательство для LLM: `[fatal]` означает гибель
  участника решения, `[injury]` — ранение, `[progress]` — продвижение миссии
- Вероятности 5 вариантов исхода хода перевзвешиваются кодом
  (`option_badness` / `reweight_probabilities` / `compute_risk_factor`):
  катастрофы вероятнее при повреждённом корпусе, высокой угрозе и доле
  рискованных решений

### Прогресс миссии

- Миссия разбита на этапы (stages), от 2 до 4
- Порог прохождения этапа — success_threshold в диапазоне **3–5** (ограничен движком)
- Прогресс накапливается нелинейно; **пройденные этапы заморожены** — регресс на них не действует
- **Регресс ограничен** — максимум −1 за ход, и только для этапа, который ещё не пройден
- **Пустой ход = 0 прогресса**: промедление и пассивные ходы не двигают миссию
- Все решения о прогрессе проходят через детерминированный **слой правил** (`game_rules.py`), который гарантирует честность

### Разнообразие миссий

Чтобы миссии не повторялись, при генерации используется система **архетипов и таблиц (random tables):**

- **13 архетипов:** первый контакт, спасение, расследование, проникновение, оборона, политическая интрига, изучение аномалии, штурм, осада, погоня, диверсия, последний рубеж, мятеж
- **4 таблицы** (выбирается по одной записи из каждой): сеттинг/локация, осложнение, сюжетный поворот, награда
- **Список запрещённых завязок** (сигнал бедствия, перехваченный сигнал, SOS…) — явно исключены из генерации
- Архетип и seeds сохраняются в БД и сопровождают миссию на всех ходах

### Командная игра

- Решения всех игроков влияют на общий исход
- Действия живых игроков имеют больший вес (HIGH), NPC — NORMAL
- NPC действуют **компетентно** в рамках своей роли — не являются источником постоянной просадки

### Корабль (персистентное состояние)

- Корпус (`hull_integrity`), щиты (`shields`) и список офлайн-систем
  (`systems_offline`) — состояние игры, которое хранится в `game_state`
  и накапливается от хода к ходу
- LLM возвращает только **дельты за ход**: `ship_hull_change` /
  `ship_shields_change` / `systems_taken_offline` / `systems_restored`;
  код применяет их к текущим значениям (кламп 0–100)
- Ремонт (`systems_restored`, положительная дельта корпуса) возможен только
  при явном ремонтном действии среди решений
- **Корпус 0 = гибель корабля** — решение принимает код (`end_game("ship_destroyed")`),
  LLM не может объявить уничтожение сам
- Состояние корабля телеграфируется в брифингах: ниже 40/100 — тяжёлые
  повреждения, ниже 20/100 — корабль при смерти

### Шкала угрозы (doom clock)

- `threat_level` 0–100 — кодовое состояние в `game_state`; тик каждый ход
  выполняет **код**, а не LLM
- Формула тика (`compute_threat_tick`): **+8** база, **+5 × доля авто-выборов**
  (промедлений) среди решений хода, **+3** при корпусе < 40%, **+2** при
  стагнации миссии (прогресс не вырос)
- **Угроза 100 → конец игры** (`end_game("overwhelmed")`) — даже если нарратив
  оптимистичен
- Шкала видна игрокам в брифингах и в пуше исхода хода; при угрозе выше
  70/100 брифинги обязаны предлагать острые, отчаянные ситуации

### Раны и лечение

- Три ступени тяжести: **minor → moderate → critical** (`wound_severity`
  персистентно хранится у игрока и NPC)
- Новая рана разрешается через лестницу `resolve_injury`: результат — максимум
  текущей и входящей ступени, рана никогда не «забывается» сама
- **Critical + любая новая рана = СМЕРТЬ** — механически, кодом
- Лечение (`crew_healed`) — только если медицинский офицер явно выбрал
  лечебное действие: ступень улучшается на шаг, `healthy` = полное излечение
- Раны телеграфируются в брифинге: раненый персонаж видит своё состояние,
  критически раненый знает, что следующая рана, скорее всего, последняя

### Смерть и зрительство

- Члены экипажа могут погибнуть — LLM адресует жертвы по **entity_id**
  (`p<player_id>` для игроков, `n<npc_key>` для NPC) в `dead_crew_members`;
  матчинг по id, fallback по точному имени из ростера
- Капов и cooldown на смерти нет — применяются все смерти, назначенные по метке
- Второй канал смерти — механический: критическая рана + новая рана
- Если погибли все (игроки и NPC) → `end_game("crew_wiped")` — достижимо,
  потому что экипаж не пополняется
- Мёртвые не-NPC игроки остаются зрителями
- Зрители видят развитие сюжета, но не влияют
- Могут переприсоединиться через /start

### Лояльность NPC и мятеж

- У каждого NPC есть **лояльность** 0–100 (`npc_profiles.loyalty`, старт 70) —
  кодовое состояние, LLM его не меняет
- Каждый ход применяется `compute_loyalty_change`: −8 за смерть (кап −16),
  −5 при уроне корпуса ≥ 15, −4 за регресс миссии, +3 за прогресс,
  +2 за лечение NPC (кап +4); итог клампится
- Лояльность видна в `/game/team` (`loyalty_band` / `loyalty_status`:
  предан / нервничает / на грани / готов взбунтоваться) и учитывается NPC
  при выборе действия
- **2+ активных NPC с лояльностью ≤ 15 → мятеж**, конец игры
  (`end_game("mutiny")`)

### Окно хода и промедление

- У каждого хода есть **дедлайн** (`game_turns.deadline`, UTC) — момент,
  когда планировщик сгенерирует следующий ход; в пуше брифинга он показан
  строкой «Ход закроется: ...»
- Планировщик шлёт **напоминания T-2h (level 1) и T-30m (level 2)** игрокам,
  ещё не выбравшим действие (`GET /game/turn-deadline/{game_id}`,
  `POST /game/remind-turn/{game_id}/{turn}`)
- Не выбравший до дедлайна получает **авто-выбор** действия от LLM
  (в характере персонажа)
- При сбое LLM авто-выбор честно фиксируется как **ПРОМЕДЛЕНИЕ**
  (`consequence_kind = "delay"`): миссию оно не двигает, а доля
  промедлений ускоряет рост угрозы
- Внутри хода всё честно: тайм-аут никогда не маскируется под осмысленный
  выбор игрока

### Матрица исходов

Итоговый вердикт игры вычисляет **код** (`compute_outcome_type`) по конечному
состоянию — LLM пишет только финальный нарратив в требуемом тоне, без
предрешённого вердикта:

- **triumph** — миссия выполнена, корпус ≥ 60%, выживших ≥ 70%, угроза < 70
- **victory** — миссия выполнена, корпус ≥ 30%, выживших ≥ 40%
- **pyrrhic** — миссия выполнена любой ценой (включая погибший корабль/экипаж)
- **stalemate** — миссия не выполнена, угроза дошла до 100, но прогресс ≥ 60%
  порогов: экипаж выжил и отступил с частью цели
- **defeat** — остальные случаи (корабль погиб, экипаж уничтожен, провал)

Причина конца (5 статусов: `mission_complete` / `ship_destroyed` / `crew_wiped` /
`overwhelmed` / `mutiny`) передаётся в финальный промпт как факт; токен вердикта
хранится в `game_state.finale_outcome_type`.

### Пост-игровая сводка

- Сразу после финала игрокам отдельным сообщением отправляется **сводка**
  (`push_game_summary`): исход, причина конца, число ходов, корпус/щиты/угроза,
  погибшие и статистика действий каждого игрока (включая число промедлений —
  `get_game_action_stats` по `player_action_stats`)
- Телеметрия по всем завершённым играм: `GET /admin/win-rate`
  (counts по токенам исходов, win_share, avg_turns, avg_auto_ratio)

### Слой правил (game_rules.py)

Между ответом LLM (`combined_outcome`) и записью в БД работает детерминированный **слой правил:**

- Нормализует этапы миссии (пороги 3–5, строгая 1-индексация)
- Применяет кэп регресса (−1) и заморозку пройденных этапов
- Применяет дельты корабля и решает гибель (корпус 0)
- Разрешает раны по лестнице (critical + новая = смерть)
- Тикает шкалу угрозы и применяет изменение лояльности NPC
- Вычисляет вердикт финала (матрица исходов)
- Гарантирует честность: LLM остаётся креативным, движок обеспечивает баланс

Чистые функции в `game-server/game_rules.py`, без БД и LLM — легко тестируются.

## Технические детали

### Архитектура системы

```text
┌─────────────────────────────────────────────────────────┐
│  Telegram Bot (aiogram)                                │

│  - Онбординг с FSM                                     │
│  - Обработка сообщений                                 │
│  - ✅ Push-сервер (порт 9090) — получение брифингов   │
└──────────────────────┬──────────────────────────────────┘
                       │
                       │ POST /push/briefings
                       ▼
┌─────────────────────────────────────────────────────────┐
│  Game Master API (FastAPI)                             │
│  - Генерация сюжета через LLM                         │
│  - Генерация изображений через ComfyUI                 │
│  - Управление состоянием                               │
│  - ✅ Push-клиент с exponential retry — отправка       │
└──────────────────────┬──────────────────────────────────┘
                       │
               ┌───────┼───────┐
               ▼       ▼
        ┌─────────┐ ┌──────────┐
        │Scheduler│ │ComfyUI   │
        │(cron)   │ │(GPU gen) │
        └─────────┘ └──────────┘
```

### База данных

- SQLite для хранения профилей, сессий, ходов, действий, сообщений, миссий
- Миссии хранятся отдельно (game_missions, mission_stages)
- Каждый ход привязан к game_id

## Заключение

AI Game Master создаёт уникальный кооперативный опыт с живой историей,
генерируемым контентом и глубокими механиками последствий.
Игроки не просто выбирают действия — они определяют судьбу экипажа и корабля.
